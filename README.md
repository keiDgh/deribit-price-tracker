# Deribit Index Price Tracker
* Сервис периодического сбора index-цен `btc_usd` и `eth_usd` с биржи Deribit и предоставления их через REST API.
* Celery Beat каждую минуту ставит задачу сбора: асинхронный клиент Deribit (aiohttp) забирает текущие index-цены, после чего они сохраняются в PostgreSQL с UNIX timestamp. 
* FastAPI отдаёт сохранённые данные через три GET-эндпоинта с обязательным query-параметром `ticker`.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2.0, PostgreSQL, Alembic, Celery, Redis (кэш + брокер), aiohttp, Docker.

## Design Decisions

### Архитектура

Проект построен по слоистой архитектуре с элементами Clean Architecture. Слои
разделены по ответственности и направлению зависимостей:

- **Domain**: сущности (`Price`, `Currency`) и интерфейсы репозиториев. Не зависит от фреймворков или инфраструктуры.
- **Application**: сервисы (`PriceService`, `CurrencyService`) и порты (`PriceCachePort`). Содержит бизнес-логику и оркестрацию.
- **Infrastructure**: FastAPI-роутеры, SQLAlchemy-модели и репозитории, клиент Deribit, Redis-кэш, Celery-задачи, настройки.

Такое разделение даёт:
- **тестируемость** - бизнес-логику можно проверять изолированно, подменяя репозитории и порты на моки;
- **гибкость** - смена способа хранения или внешнего API не затрагивает доменный слой;
- **явные границы** - по структуре директорий сразу видно, где какая ответственность.

### Другие решения
- **Кэширование `/prices/latest`.** Стратегия Cache-Aside. Redis с TTL (5 минут). Инвалидация: в нормальном режиме значение перезаписывается свежим до истечения TTL, запас нужен как страховка при сбое воркера или перезапуске Redis.
- **Обработка ошибок.** Сетевые сбои и retryable HTTP-статусы (408, 429, 5xx) ретраятся с экспоненциальным backoff и jitter. Бизнес-ошибки Deribit (JSON-RPC `error`) не ретраятся, повторный запрос даст тот же ответ.
- **Миграции в lifespan backend'а.** Упрощает запуск: `docker compose up` поднимает всё одной командой. При горизонтальном масштабировании backend'а миграции следует вынести в отдельный сервис.
- **Redis как брокер и backend Celery.** Redis уже используется как кэш, поэтому добавление RabbitMQ избыточно для текущего объёма задач. При росте нагрузки стоит перейти на RabbitMQ.
- **Эндпоинты `/prices`, `/prices/latest`, `/prices/history`.** Формально REST требует выражать фильтры через query-параметры одного ресурса, но задание выделяет три сценария. `latest` и `history` трактуются как под-ресурсы коллекции, а не как операции.

### Модель данных

Вместо хранения тикера строкой в таблице `prices` используется отдельная таблица `currencies` и внешний ключ `currency_id`.

**Плюсы:**
- нормализация - нет дублирования названий валют;
- легко расширять список валют (добавить `sol_usd` - одна строка в seed);
- можно добавлять метаданные валюты, не меняя таблицу `prices`.

**Минусы:**
- запросы чуть сложнее - нужен `JOIN` с `currencies`;
- требуется seed при старте.

Для текущего объёма данных (2 валюты, 1440 записей в сутки на валюту) накладные расходы минимальны, а выигрыш в читаемости и расширяемости есть.

### Защита от дубликатов
На таблицу `prices` добавлен составной уникальный ключ `UniqueConstraint(currency_id, timestamp)`. Это защита от дубликатов при повторном срабатывании задачи — перезапуске worker'а или beat'а, гонках между процессами, ручном запуске таски.

При нарушении ограничения репозиторий поднимает доменное исключение `DuplicatePriceError`.

### Получение цен (Celery)
Периодический сбор реализован через Celery worker, Redis как брокер и backend, Celery Beat
Интервал задаётся через переменную окружения `COLLECT_INTERVAL_SECONDS` (по умолчанию `60`).

### HTTP-клиент к Deribit
Используется `aiohttp` (опциональное требование ТЗ). Клиент обёрнут в класс `DeribitClient` с:

- явными доменными исключениями `ExternalServiceTransientError` / `ExternalServiceBusinessError`;
- retry через `tenacity` **только для транзиентных ошибок** — 5xx, таймауты, сетевые сбои;
- таймаутами на соединение и чтение.

Такое разделение позволяет задаче сбора различать «можно повторить» и «данные некорректны, ретраить бессмысленно».

### Кэширование последней цены
Для эндпоинта "последняя цена" добавлен простой кэш в Redis (`PriceCacheService`):
- ключ — тикер (`price:latest:btc_usd`);
- TTL задаётся через `CACHE_TTL_SECONDS`;
- при недоступности Redis сервис идет в БД

Кэш не является источником истины и не усложняет основную логику записи: данные обновляются Celery-таском раз в минуту, кэш лишь снижает нагрузку на БД при частых запросах последней цены.

### API

Все обязательные методы — GET с обязательным query-параметром `ticker`:

`GET /prices`: Все сохранённые записи по тикеру (с пагинацией) 
`GET /prices/latest`: Последняя цена 
`GET /prices/history`: Цены за диапазон дат. Фильтр по дате принимает `datetime` - удобнее для клиентов, чем сырые UNIX-timestamp'ы.

### База данных и миграции
- PostgreSQL + SQLAlchemy 2.0 (async) + asyncpg.
- Миграции - Alembic в async-режиме (`run_sync` внутри async-engine).
- Миграции и первичный seed валют выполняются при старте приложения (lifespan FastAPI).

### Конфигурация

Все настройки вынесены в переменные окружения и читаются через `pydantic-settings`. Это упрощает запуск в Docker и локально без изменения кода.

### Что сознательно не усложнялось
- Нет аутентификации / авторизации — не требовалось ТЗ.
- Нет rate-limiting и сложной обработки ошибок API сверх базовых HTTP-кодов.
- Нет фоновых метрик и структурированного логирования — чтобы не раздувать объём тестового задания.

Unit-тесты можно добавить отдельно; архитектура к ним готова — порты и DI позволяют подменять зависимости на моки.


## Запуск

1. **Клонировать репозиторий**

Из Github: **git clone https://gitlab.com/keidgh_123/deribit-price-tracker.git**

Перейти в директорию: **cd workspace_service**

2. **Создать .env**
```   
APP_NAME=deribit-price-tracker

POSTGRES_USER=postgres

POSTGRES_PASSWORD=postgres

POSTGRES_DB=deribit_price_tracker

POSTGRES_HOST=postres

POSTGRES_PORT=5432

REDIS_PORT=6379

REDIS_HOST=redis

CACHE_TTL_SECONDS=300

DERIBIT_API_URL=https://www.deribit.com/api/v2

COLLECT_INTERVAL_SECONDS=60
```

3. **Открыть Docker Desktop**
Убедитесь, что Docker Engine запущен

4. **Запустить приложение**
**docker compose up --build**

Если образ уже собирался:  **docker compose up**
